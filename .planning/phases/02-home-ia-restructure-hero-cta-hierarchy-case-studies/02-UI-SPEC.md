# Phase 2 — UI Design Contract

> Visual and interaction contract for the home page hero rebuild, CTA hierarchy, and 5-case activation.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase touches only `src/routes/index.tsx` (hero section + new case-studies section, inserted
between Brand Marquee and Positioning). No new CSS file, no new npm dependency. Every value below
either reuses an existing token/class verbatim or extends `src/styles.css`'s `@layer components`
using the exact same authoring convention already in that file.

## Spacing Scale

Declared values (multiples of 4, matches the 8-point scale already implicit in the codebase's
`gap-4`/`gap-8`/`gap-12`/`mt-12` usage):

| Token | Value | Usage this phase |
|-------|-------|-------|
| xs | 4px | Icon-to-label gap inside CTA buttons (existing `.btn` `gap: 0.5rem` = 8px, see exception) |
| sm | 8px | `gap-2` between icon and label in CTA buttons |
| md | 16px | `gap-4` between buttons within the primary CTA cluster row; `gap-y-16`/`gap-x-8` inside the case-card grid |
| lg | 24px | `mt-6` figcaption spacing (existing `ProjectCard` convention, unchanged) |
| xl | 32px | `mt-8` gap between the primary CTA cluster row and the secondary "Ver Portfolio completo" text-link |
| 2xl | 48px | `mt-12` gap between headline block and CTA cluster (existing hero convention, reused) |
| 3xl | 64px | `gap-16` between hero text column and hero photo column on `lg:` breakpoint |

**Exceptions:**
- `.btn-hero-primary` / `.btn-hero-secondary` padding is `1.125rem 2.25rem` (18px/36px) — not a clean
  multiple of 4. This is an **existing, unmodified class** reused verbatim from `src/styles.css`; this
  phase does not redefine it, so it is grandfathered in rather than "fixed" mid-phase.
- Hero photo card `max-width: 420px` is a fixed pixel value tied to the 4:5 aspect ratio math, not the
  8pt rhythm — acceptable for a container-sizing constraint, not a spacing token.

## Typography

Scoped to the new/changed elements this phase introduces. All other type on the page (h2–h6, existing
body copy) is untouched and already declared in `src/styles.css` — not re-specified here.

**4 sizes declared this phase:**

| Role | Size | Weight | Line Height | Where used |
|------|------|--------|-------------|------------|
| Display (hero result line) | `clamp(1.5rem, 2.5vw, 2.75rem)` (24–44px) | 700 | 1.1 | H1 line 2 — the delivered-result statement |
| Heading (hero role line) | `clamp(2rem, 3.5vw, 4rem)` (32–64px) | 700 | 1.05 | H1 line 1 — the role statement |
| Body (P→A→R sentences) | `0.875rem`/14px | 400 | 1.6 | Problem/Action/Result `<dd>` sentences inside each case card |
| Label (kicker, tags, P→A→R `<dt>`, CTA button labels) | `0.75rem`/12px, uppercase | 700 | 1.4, `letter-spacing: 0.05em`–`0.1em` | Case category tags (reuses existing `.site-card-label`, 0.75rem — no change); hero role-line kicker (if used as a small eyebrow above H1 — see Layout Decisions); P→A→R "Problema:"/"Ação:"/"Resultado:" bold inline labels; LinkedIn/E-mail/CV/Ver Portfolio CTA button text |

**Case-card `<figcaption>` name — not a 5th size, grandfathered:** the 5 case-card titles reuse the
**existing, unmodified** `.project-card figcaption` class already declared in `src/styles.css`
(`font-size: 1.2rem; font-weight: 500; line-height: 1.3`). This is untouched sitewide convention — the
same class already renders every project title on `/trabalho` and elsewhere — so it is not a new
typographic value introduced by this phase, the same way `.btn-hero-primary`'s padding is grandfathered
in the Spacing section above. No `1.125rem`/18px value is introduced.

**CTA button label sizing note:** `.btn-hero-primary` / `.btn-hero-secondary` currently ship at
`0.8125rem`/13px in `src/styles.css` (existing, unmodified declaration). To keep this phase's Label tier
at a single unified value (12px) across tags, kicker, and CTA text, the CTA `<a>` elements in the hero
cluster (Layout Decisions §3) add the Tailwind utility `text-xs` (0.75rem) alongside the existing
`btn btn-hero-primary`/`btn btn-hero-secondary` classes. Tailwind's utilities layer loads after the
`@layer components` block in this project's Tailwind v4 setup, so `text-xs` wins the cascade over the
component class's `font-size: 0.8125rem` without editing the existing class definition itself.

**Weights used, exactly 2:** `400` (regular — body/P-A-R sentences) and `700` (bold — all headings,
labels, and button text). No new weight is introduced; this matches the sitewide rule already declared
in `src/styles.css` (`h1–h6 { font-weight: 700 }`, body `font-weight: 400`).

## Color

| Role | Value | Usage this phase |
|------|-------|-------|
| Dominant (60%) | `#f4f4f4` (`--background`) | Hero section background — **stays light, no `bg-foreground` inversion** (see Layout Decisions §1). Case-studies section background. |
| Secondary (30%) | `#ffffff` (`--card`) / `#6b6b6b` (`--secondary`) | Hero photo card border/frame background; case-card `media-wrap` fallback background (`#e0dede`, existing); P→A→R sentence body text color (`text-secondary`) |
| Accent (10%) | `#252422` (`--foreground`) | Reserved for: (1) hero H1 text (both lines), (2) the single filled primary CTA button (LinkedIn), (3) P→A→R bold inline `<dt>` labels ("Problema:"/"Ação:"/"Resultado:"), (4) case-card title text, (5) hover-state fills on the two outline CTA buttons (E-mail, CV) and on `.btn-hero-secondary`/`.text-link`. Not used for anything beyond this list — no new accent color is introduced. |
| Destructive | `#000000` (`--destructive`, token exists) | Not applicable this phase — no destructive actions exist in the hero or case-studies section (all CTAs are non-destructive navigation/contact actions) |

**Accent reserved for:** hero H1 text, the one filled LinkedIn button, P→A→R bold labels, case-card
titles, and hover-fill states on outline buttons/text-links — never applied to more than these listed
elements. This directly follows `PITFALLS.md` Pitfall 7 (already cited in `02-RESEARCH.md`): hierarchy
is expressed through fill-vs-outline-vs-text-link tiering of the existing foreground/background pair,
not through a new brand color.

**ui-ux-pro-max informed this decision:** a `--design-system`-style domain search against this
codebase's actual tokens (`--background:#f4f4f4`, `--foreground:#252422`, 12-column grid, 8px base
unit) matches the skill's **"Swiss Modernism 2.0"** style entry almost exactly (`#000000`/`#FFFFFF`/`#F5F5F5`,
grid system, single accent only, high WCAG AAA accessibility, "no decorations"). That entry's guidance —
single accent, mathematical 8px spacing, high contrast, no gratuitous shadows — is the basis for keeping
the hero on its native light background and expressing CTA hierarchy purely through fill/outline/text-link
tiering rather than a new color.

## Layout Decisions (resolves 02-RESEARCH.md's Open Questions 1–3 and Discretion items)

These are the specific, executable answers the planner/executor should build against. Each corresponds
to an item `02-RESEARCH.md` explicitly deferred to this UI-SPEC step.

### 1. Hero section background stays light — no dark inversion

**Decision:** The hero section keeps the site's default `#f4f4f4` background (`--background`). It is
**not** given a `bg-foreground text-background` inversion. This directly answers `02-RESEARCH.md` Open
Question 1, per the explicit user-confirmed correction carried into this UI-SPEC session: the site is a
light/editorial design with *pointed local inversions* (e.g. the existing "Positioning" section), not a
global dark theme — inverting the hero would introduce a new, unrequested visual pattern not asked for
by any Phase 2 requirement.

**Consequence for photo compositing:** Since the hero background and the photo's own studio backdrop
are both near-white, there is no light-on-dark clash to solve. The "feathered mask vs. dark canvas"
framing inherited from `01-HERO-PHOTO.md` §7 does not apply. Instead:

**Decision — hero photo treatment:** Reuse the exact existing card convention already used for every
`ProjectMedia` wrap in this codebase, adjusted only in aspect ratio:

```tsx
<div className="media-wrap aspect-[4/5] rounded-2xl overflow-hidden border border-border/5 max-w-[420px] mx-auto lg:mx-0 lg:ml-auto">
  <picture>
    <source
      type="image/avif"
      srcSet="
        /assets/home/hero/murilo-hero-480.avif 480w,
        /assets/home/hero/murilo-hero-960.avif 960w,
        /assets/home/hero/murilo-hero-1440.avif 1440w
      "
      sizes="(min-width: 1024px) 420px, (min-width: 640px) 360px, 85vw"
    />
    <img
      src="/assets/home/hero/murilo-hero-960.jpg"
      srcSet="
        /assets/home/hero/murilo-hero-480.jpg 480w,
        /assets/home/hero/murilo-hero-960.jpg 960w,
        /assets/home/hero/murilo-hero-1440.jpg 1440w
      "
      sizes="(min-width: 1024px) 420px, (min-width: 640px) 360px, 85vw"
      alt="Murilo Ortega"
      width={960}
      height={1200}
      loading="eager"
      fetchPriority="high"
      className="w-full h-full object-cover"
    />
  </picture>
</div>
```

No new `mask-image` CSS class is introduced. This is a deliberate choice over `02-RESEARCH.md`'s
"Primary recommendation" (a feathered mask): the mask solves a color-clash problem that doesn't exist
at these token values, whereas the bordered-card treatment reuses a pattern the codebase already has
zero-risk precedent for (`ProjectMedia` wraps sitewide) — lower implementation risk, visually
consistent with the case-card treatment introduced later in this same page.

### 2. Hero grid layout and `sizes` (resolves Open Question 2)

**Decision:** `grid-cols-1 lg:grid-cols-[1.4fr_1fr] gap-12 lg:gap-16 items-center`, text column first
in DOM order (unchanged from current hero), photo column second — no reordering on mobile. The photo
card is capped at `max-width: 420px` and right-aligned within its column on `lg:` via `lg:ml-auto`.

`sizes` value (both AVIF `<source>` and JPEG `<img>` fallback): `"(min-width: 1024px) 420px, (min-width: 640px) 360px, 85vw"`.
`width={960} height={1200}` on the `<img>` (4:5 ratio, prevents CLS regardless of which srcset tier the
browser picks) — copied verbatim from `01-HERO-PHOTO.md` §5's guidance.

### 3. Hero CTA cluster structure (resolves Discretion item — Option A vs. B from 02-RESEARCH.md Pattern 3)

**Decision:** Neither pure Option A (three identical filled buttons) nor pure Option B (icon-only
secondary buttons). A **three-tier hybrid**, all three visible-label:

```tsx
<div className="mt-12 flex flex-wrap gap-4 anim-fade-in delay-500">
  <a href="https://www.linkedin.com/in/murilo-ortega" target="_blank" rel="noopener noreferrer" className="btn btn-hero-primary gap-2 text-xs">
    <Linkedin size={16} /> Conectar no LinkedIn
  </a>
  <a href="mailto:contato@muriloortega.com" className="btn btn-hero-secondary gap-2 text-xs">
    <Mail size={16} /> Enviar E-mail
  </a>
  <a href="/cv/CV%20MURILO%20ORTEGA%202026.pdf" download className="btn btn-hero-secondary gap-2 text-xs">
    <Download size={16} /> Baixar CV
  </a>
</div>
<div className="mt-8 anim-fade-in delay-500">
  <Link to="/trabalho" className="text-link">
    Ver Portfolio completo
  </Link>
</div>
```

`text-xs` (0.75rem/12px) is added to each CTA `<a>` so button labels match the unified Label-tier size
declared in Typography above, overriding `.btn-hero-primary`/`.btn-hero-secondary`'s existing
`font-size: 0.8125rem` via Tailwind's utilities-after-components cascade — no edit to the existing class
definitions themselves.

**Rationale:** LinkedIn is the single filled `.btn-hero-primary` (highest weight — it's the action a
recruiter is most likely to take and most likely to already have an account/session for). E-mail and CV
use the existing outline `.btn-hero-secondary` class, grouped in the same row — together the three form
"the cluster" that Roadmap success criterion 2 requires to read as visually dominant versus everything
else in the hero. "Ver Portfolio completo" is demoted one tier further, to the existing `.text-link`
component (plain underlined text, no button chrome) — this creates unambiguous 3-level hierarchy
(filled > outline > text-link) using zero new classes, and avoids the "three identical heavy black
buttons" kitchen-sink risk `02-RESEARCH.md` Pitfall/PITFALLS.md Pitfall 7 flags for pure Option A, while
avoiding the accessibility softness of icon-only buttons in pure Option B. All labels are copied
verbatim from Phase 1's already-corrected values — LinkedIn URL and CV path must exact-match
`https://www.linkedin.com/in/murilo-ortega` and `/cv/CV%20MURILO%20ORTEGA%202026.pdf` (Pitfall 1).

WhatsApp is absent from this row entirely (ANTI-04) — not demoted, simply not rendered; Phase 3 owns
where it reappears (final contact block, subordinate).

### 4. Case-study card grid (resolves Open Question 3)

**Decision:** `grid-cols-1 md:grid-cols-2 lg:grid-cols-3 gap-x-8 gap-y-16`. Natural grid flow — no
spanning/centering rules for the 5th card. At `lg:`, row 1 holds 3 cards, row 2 holds the remaining 2
left-aligned (empty 3rd cell, no forced centering). This is the lowest-risk option: no new CSS, matches
the Swiss/grid-based aesthetic ui-ux-pro-max's "Swiss Modernism 2.0" entry recommends for this token set,
and avoids inventing an asymmetric "featured card" treatment not asked for by any requirement.

Card order (top-to-bottom, left-to-right): NaTrave, Symplice, Maxi, Solid+, Kapyi — matches
`02-CONTEXT.md`'s D-01 confirmed list order.

Each card reuses the existing `ProjectCard` component's `media-wrap aspect-[4/3] rounded-2xl overflow-hidden border border-border/5`
wrapper (unchanged aspect ratio — this is the existing project-thumbnail convention, distinct from the
hero photo's 4:5), extended per `02-RESEARCH.md` Pattern 2's `<figcaption>`/`<dl>` structure. All 5 card
images use `loading="lazy"` (the `ProjectMedia` default) — `loading="eager"`/`fetchPriority="high"` is
reserved for the hero photo only (Pitfall 2). Card image source: `thumbnails/*.jpg` paths listed in
`02-RESEARCH.md`'s Code Examples — never `solid-full.png` (8.2MB, wrong asset for this context).

### 5. `HeroGallery` removal (resolves 02-RESEARCH.md Pitfall 3 / Assumption A3)

**Decision:** Remove the `HeroGallery()` component call from the hero's rendered JSX (the hero's right
column becomes the photo card from §1–2 above, not the gallery). The `HeroGallery()` function,
`galleryImages`, and `galleryAlts` arrays may be deleted from `index.tsx` outright — every image they
reference remains independently reachable via `/trabalho` and each project's own route, so no visual
asset or page is lost; only one hero-specific UI pattern (the scrolling gallery) is retired. This is a
UI-layer call the executor should still flag explicitly in the plan/PR description for visibility, per
`02-RESEARCH.md`'s own recommendation, even though this UI-SPEC resolves the ambiguity.

### 6. Hero supporting paragraph

**Decision:** The current hero's descriptive `<p>` below the H1 ("Design que confronta o comum e eleva
o digital...") is removed. Its message is superseded by the two-line H1 itself (role + result). This is
a copy rewrite of hero marketing text, not a deletion of project/page content, so it does not conflict
with the project's non-negotiable "nothing existing may be deleted" constraint (which governs
projects/pages/assets, not in-place hero tagline copy that HERO-01 explicitly asks to be rewritten).
